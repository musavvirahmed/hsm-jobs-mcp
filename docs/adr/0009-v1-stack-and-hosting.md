# v1 stack and hosting (Workers + D1 + batch crawl)

**hsm-jobs-mcp** v1 answers from a durable **jobs index** — MCP tools never scrape on demand. Query plane: Cloudflare Workers serving `GET /`, Streamable HTTP `/mcp`, and `/health` on **`https://hsmjobs.musavvir.work`**. Store: Cloudflare **D1** (one growing corpus from **partial index** / private through **full careers pass** / shared). Crawl plane: scheduled job (e.g. GitHub Actions) and/or operator CLI writing D1 — not inside the Worker request path; always-on crawler only if batch proves insufficient later. Cadence: ~daily Opening refresh for known paths; on **register refresh** / new KvKs, immediately attempt missing **terminal careers outcomes** and re-**partial** until caught up ([ADR 0004](./0004-partial-index-ship-rule.md)). Ops: free-tier first; `/health` (coarse) + **`get_index_status`** (scope, crawl freshness, upstream **hsm-mcp** degrade) + alert on repeated crawl failure; dashboards/paging post-v1. Private path uses the same stack (`wrangler` + D1); dense spec must include a Cloudflare bootstrap wizard. DNS/D1/deploy wiring is **implement**-time, not planning-time. Contrast **hsm-mcp**: register in KV + DO SQLite for agent/scraper — not the jobs-index pattern.

**Considered options:** scrape-inside-tool; throwaway local DB then rebuild for shared; SQLite-file-as-primary with manual copy; KV-as-primary jobs store; always-on crawler in v1; paths on the same host as hsm-mcp; Datadog-style APM/paging in v1; paid CF from day one; inventing Cloudflare only because hsm-mcp uses it without locking D1/Workers deliberately — rejected for false emptiness, dual schemas, weak search, cost/ops drag, or packaging dishonesty.
